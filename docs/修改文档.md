# Bug 1：背景识别误判，6 张白底图被当成复杂背景跳过

现象：首次跑 8 张样本，只有 1 张成功，其余 6 张白底图全部报"检测到复杂背景"跳过。
根因：detect_mode 用**边框颜色的标准差 σ** 判断是否为纯色背景：

    std = float(border.std(axis=0).mean())
    if std > 18.0: return COMPLEX

  但 deepseek.jpg 等样本的**右下角被主体占据**，主体像素混进边框采样后把 σ 大幅拉高，
  于是误判成复杂背景。
经验：**中位数扛得住少数派，标准差扛不住**。主体占角是少数派污染，却足以炸掉 σ。
修复：改用**内点占比**判定——先取边框中位色作为背景代表色，再统计边框像素中
  与该色距离 < 45 的占比；占比 ≥ 55% 即判为纯色背景（即使某边角被主体占据也没关系）。

    inlier_ratio = float(np.mean(inlier_dist < 45.0))
    if inlier_ratio < 0.55: return COMPLEX

验证：修正后 8 张样本全部识别正确，7 张输出透明 PNG、1 张复杂背景按预期跳过。

# 边缘残留白边：用合成公式反解前景色

现象：白底图抠完后主体边缘有一圈浅白光晕，叠到深色背景上很明显。
根因：原图像素是"前景与白背景混合后的结果" C = α·F + (1−α)·B，
  边缘像素 α<1，颜色里混着背景白，直接输出就带白边。
修复：refine.py 新增 despill()，只对半透明边缘像素反解前景色，α 设下限 0.2 防数值爆炸：

    fg = (rgb[edge] - (1.0 - ae) * bg) / ae_safe

验证：deekseep3.jpg 边缘像素"白度"（三通道最小值均值）**212 → 169**。

# 诊断 Case A：deepseek4.png 已有 alpha 却被重复抠图，深色主体被误删

现象（用户反馈）：角色里面是白色的部分被去除了；合成红底时露出背景。
诊断（实证数据）：
  - 打印原图 alpha 分布：**0 占 39.61%、254 占 58.54%、中间值仅 0.64%**，
    二值占比 99.5%，边框透明率 100% —— 这张图**早就抠好了**。
  - 以原 alpha 为真值比对：我们的结果误删 **25354 个主体像素（占主体 2.7%）**，
    这些像素**平均亮度只有 16**（接近纯黑）。
根因：抠好的 PNG，透明区下方的 RGB 通常被压成**纯黑**（保存机制所致）→
  detect_mode 看到边框发黑判为"黑底图" → 又按黑色重新抠一遍 →
  主体上离黑色近的部分（深蓝裙子、头发暗部）被当成背景删掉。
性质：**设计缺陷，不是算法 bug**——对已经抠好的图做了重复劳动。
诊断产物：output/debug/_诊断_误删.png（被删像素标红）。

# 诊断 Case B：deepseek2.png 白色衣领（颜色方法的原理天花板，不可修）

现象（用户反馈）：角色白色的**衣领**被当成背景删掉，叠红底时露出红色。
根因：这是头部特写，衣领在画面**底部被裁断**，没有完整描边把它与背景隔开。
  算法看到的是"从画面底部边缘进去一大片白色"，无从分辨哪里是背景、哪里是衣领。
  两者 RGB 数值几乎相同，且**像素直接连通**。
实验（证明不是 bug 也不是调参能救）：把判定收紧到只有距离背景色 <10（近乎纯白才删）
  再从边界向内扩散：

    当前方案 删 11557 px / dist<10 删 11121（只少 436）/ dist<20 11292 / dist<35 11418

  **即使收紧到极致也只能救回 436 px**。
另一组佐证：统计"距画面边界 >25px 的深层被删像素 = 0"，说明**不是主体内部被掏空**
  （连通域修正工作正常，对该图恢复了 12.3% 的内部白区），
  而是轮廓边缘那圈白色部件与外部背景连成一片一起被吃掉。
补充：现有 flood fill **已把角色深色描边当屏障**（只在接近背景色的区域扩散），
  所以大多数图能挡住；失效只发生在"主体白色部件被画面边缘裁断"这种场景。
结论：留给二期 AI 语义分割 + 三期手动指定；此图作为 **M5 的验收样本**。
用户同时确认一条重要设计原则：**不能设计成"角色内部一律不删"**——
  手臂空隙、提手镂空、双腿缝隙本质上就该删，判据必须是语义/轮廓/人工，而非"是否在内部"。
诊断产物：output/debug/_衣领对比.png（原图 / 当前方案 / 严格洪水填充候选）。

# 修复次生问题：alpha=254 被当半透明 + 透明区黑边渗出

1) refine.harden_alpha()：深查发现原图主体 alpha 大面积是 **254 而非 255**
   （占 58.5%，纯 255 仅 0.10%），部分软件会当半透明处理。
   修复：两端吸附（≤16→0、≥240→255），**保留中间过渡带**，不破坏真实存在的半透明边缘。

    out[out <= lo] = 0
    out[out >= hi] = 255

2) refine.extend_edge_color()：透明区下方 RGB 是纯黑，二次缩放/合成时黑边会渗进边缘。
   修复：把边缘色向未知区域逐轮平均扩散（每轮 1 像素），**只改写 alpha==0 区域**：

    acc = np.stack([cv2.blur(out[:,:,c] * kf, (3,3)) for c in range(3)], axis=2)
    newval = acc / np.maximum(weight[:,:,None], 1e-6)
    out[updatable] = newval[updatable]

两者只在沿用分支生效，不进颜色抠图路径——避免把软阈值生成的过渡带压死。

2026.10.10 关键经验总结

1. 纯色背景判定**不要用四个角点采样，也不要用颜色标准差**——真实图片的角落经常被
   主体占据。正确做法：边框中位色做代表色 + 统计内点占比（本项目 Bug 1）。
2. JPEG 的白底是 252~254 的"近白"，不是纯 255，阈值必须留余量。
3. 处理带 alpha 的输入前，**先判断它是否已经抠好**——抠好的 PNG 透明区下方 RGB 是黑的，
   直接按黑底重抠会删掉主体的深色部分。检测条件：alpha 二值占比 + 边框透明率。
4. "已经在内部"不等于"应该保留"：手臂空隙、圆环镂空、双腿缝隙本质属于背景；
   判据只能是语义理解 / 轮廓描边 / 用户指定。
5. **"某个像素该不该删"这个问题，纯颜色方法存在原理天花板**：白色主体部件若在画面边缘
   被裁断，它与背景颜色相同且像素连通，任何颜色规则都救不回来。判断某个方案"能不能做"
   时，用极限实验（把阈值收紧到极致看能救回多少）比反复调参更快得出结论。
6. 验证抠图效果：把结果叠到**红底**上比棋盘格更容易暴露白边与误删。
7. 每出一次不符合预期的结果，先分清是 **bug（可修）** 还是 **方法限制（不可修）**，
   再决定投入：前者改代码，后者记入文档并排到对应阶段。
8. 涉及 numpy 的 alpha 处理，除法一定给 α 设下限（如 0.2），否则半透明像素会数值爆炸。
9. 该环境下 pip 装包不可靠，用 curl 直连清华源下载 whl 再本地安装；whl 文件名必须
   保留完整版本/平台标识。
10. 文档写完必须**回读校验**——本项目出现过"以为写了 v0.2 实际仍是 v0.1"的事故。

# 增强 4：不带参数运行时弹出文件选择窗口

现象：用户在 PyCharm 里右键 `src/main.py` → Run，终端打印一大串用法后退出：

根因：不是依赖没装，而是**没传命令行参数**。argparse 里 `-i/--input` 定义为 `required=True`，
PyCharm 右键运行默认不带任何参数，于是 argparse 打印用法并以退出码 2 结束。
这是个**交互设计缺陷**：用户想要的是"选图→导出"，CLI 却要求先背参数写法。

（Python 标准库自带，**不引入任何新依赖**，也不与 M2 计划中的 PySide6 冲突，
M2 上线后本节可保留作为命令行侧的兜底）。选完自动逐张处理，结果落到原图所在目录的 `output/` 下。

关键防御：tkinter 在无图形界面的环境会抛异常，这种情况不能崩，改为打印可直接复制的命令行示例。

~~~python

    from tkinter import filedialog
    root = tkinter.Tk()
    root.withdraw()
    root.attributes("-topmost", True)

        title="选择要处理的图片（可多选）",

    return list(paths)

# argparse 定义：required=True -> default=None
p.add_argument("-i", "--input", default=None,

# main() 入口处拦截

~~~

`_run_interactive()` 内部用 try/except 包住弹窗，失败时调用 `print_usage_hint()` 返回码 2；

# M9 交互增强：中键平移 / 多区域描边 / 三级撤销 / 框内保留与框内去除

现象（用户一次性提了 4 条，并授权所有决策由我拍板）：
  ① 软件里不能拖动图片，描边时操作困难；
  ② 描边没有回退，画错了只能全部取消重新画；
  ③ 描边只能描一个区域，多个区域的线段不能断开，会连到下一个区域里；
  ④ 想要「框内保留 / 框内去除」——比如之前把衣服也去掉了的情况，
     希望能在衣服上描一圈把它留下。同时追问一个关键问题：
     **"如果先按默认算法处理，再描边，再运行一次，还会保留吗？
       这个保留是按原图还是按处理后的图片？"**

第 ④ 条的追问是这次设计的核心，先给结论再写实现：

  决策 D9  人工保留/去除存为**独立裁决层**（keep_mask / drop_mask，原图坐标），
           不与算法结果混算，只在算法跑完后叠加 → 再点几次「开始处理」都不会丢。
  决策 D10 裁决**优先于算法**；保留区若原本被判成背景，颜色用**原图 RGB** 回填
           （用户要的是衣服本来的颜色，不是算法在透明区留下的灰黑）。
  决策 D11 描边支持多区域，且改为**显式提交**（Enter / 「应用选区」）。
  决策 D12 撤销分三级：草稿顶点 → 已闭合区域（退为草稿，不是丢弃）→ 已提交修改。

# M11 画质修复：处理后浅色内部部件残留半透明（眼睛高光发灰）

现象（用户实测，附处理前后眼睛对比图）：

  底部白色围裙同样有发灰透底的观感。

根因（两处半透明 bug，一深一浅）：
根因 ①（浅层）：`colorkey.keep_border_connected` 的洞判定阈值取 `thr=128`。
    它把"与边框连通的 alpha<128"当背景，于是主体内部那些 alpha 落在
    [128,254] 的像素既不算背景、也不算前景，被**永久留成半透明**。
    眼睛高光 RGB≈(205,223,239)，到白底色差仅 55~79，正落在软阈值 [30,80] 内
    → alpha≈160，又被深蓝眼珠完全包住（不与边框连通）→ 命中这个 bug。
根因 ②（深层）：`ai_segment.rescue_subject` 把 AI 的**软 alpha（置信度）**直接写进结果。
    AI 的 alpha 不是真正的透明度，restore 区虽已限定 ai_alpha≥170（置信度足够高、
    本应就是前景），却写成 170~249 的软值；更麻烦的是它把 AI 主体 subj（比颜色前景大）
    填实后，会把某些原本连通到边框的背景"围"成内部洞——这些洞的 alpha 也是 156~249，
    于是主体内部出现成片半透明（实测 deepseek.jpg 因此多出 3423 个内部半透明像素）。

  ① `colorkey.keep_border_connected`：判定"背景候选"的阈值由 128 提到 **250**

     背景（与边框连通那一块）不受影响，边框透明率不下降。
  ② `ai_segment.rescue_subject`：
     - 不再逐像素写 AI 软值，改为**整块 restore 直接置 255**（硬前景）；

       恢复为 255（只修不与边框连通的洞，genuine 背景保持原样）。

经验：
  1. "置信度"和"透明度"是两种东西，绝不能互相赋值。AI 分割输出的 alpha 是

     背景围成内部空洞；这类"填实引入的新洞"只有填完再跑一次连通域才能被发现，
     光看逐像素的赋值逻辑是想不到的。

     定位手法：把 alpha 与"边框连通性"挂钩，找出"不与边框连通却 <255"的像素——
     这些就是主体内部的半透明脏斑，数量、位置一列就清楚。

# M12：修复 onnxruntime 在 1024×1024 连跑第二张图 "bad allocation"

现象：同一进程里用 BiRefNet 连跑两张图，第二张直接抛 `bad allocation`
（偶发伴 `numpy.core._exceptions._ArrayMemoryError`）。

根因：BiRefNet 单次 1024×1024 推理的中间张量很大，onnxruntime **默认的内存池

第二张即失败——并非真的"内存不够"，而是内存池不释放。

修复（core/hq_segment.py::_get_session）：
    opts.intra_op_num_threads = 0
    opts.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
    opts.enable_mem_pattern = False       # 不复用中间张量内存布局
    opts.enable_cpu_mem_arena = False     # CPU arena 不预占大块内存

改动文件：
  - src/core/hq_segment.py  _get_session 增加两行关键选项

验证：连跑 4 轮，可用内存稳定在 8.2GB 不下降（测试 [13] 专门守这条）。

# M13：修复"先保留过的区域，后画去除不生效"（裁决层语义）

现象：用户先对某区域提交了「保留」，之后切到「去除」对**同一区域**再画
（描边/点选均可），点「应用选区」后该区域纹丝不动，仍是不透明。

根因：`gui.py::_on_commit` 末尾有一行旧逻辑（M9 决策 D13 的实现）：

    self._drop_mask[self._keep_mask > 0] = 0

它无条件让"保留"赢——本意是"同一笔里既画保留又画去除时以保留为准（防误删）"，
但写在了**跨笔合并**的位置上，等于保留一旦画下就永久占据该像素，
后来任何「去除」都会被这行清掉。用户视角就是"去除没生效"。

修复（interactive.py 新增 `merge_override_masks()`，gui 调用之）：
- 跨笔合并改为**后画的覆盖先画的**：新去除清掉旧保留标记、新保留清掉旧去除标记；
- "保留优先"只保留在**同一笔提交内部**重叠时（防误删语义不变），与
  apply_override 的叠加顺序（先 drop 后 keep）一致；
- 该函数为纯函数（不修改入参），单测直接覆盖。

改动文件：src/core/interactive.py（新增 merge_override_masks）、
src/ui/gui.py（_on_commit 重写 + 新增 _build_selection_masks、删除 _or_mask）。

# M13：修复"点选去除被当成保留"+ 处理后涂抹圆点残留

现象①：作用=去除时用「点选」左键涂红点，应用后红点区域反而被**保留**。
现象②：画了点选后直接点「开始处理」（没按 Enter/应用选区），
涂抹完全不生效，且画面上的彩色圆点一直残留。

根因①：`_on_commit` 里把画布的 bg_pts（红点）一律当作"当前作用的**反面**"：

    _add(bg_pts, "drop" if action == "keep" else "keep")

这是 M10 把点选改成"笔刷直写裁决层"时留下的逻辑——当时的交互是
"fg_pts=当前作用、bg_pts=右键反面"，提交时需要按 action 反推。
但 M10 之后画布绘制时**已经**按当前作用把点分好色了
（左键涂当前作用色→_fg_pts 绿，右键涂反面→_bg_pts 红），
提交时再反推一次就把语义弄反：作用=去除时，左键涂的红点（存于 bg_pts）
被反推成"keep"。正确做法是**颜色即语义**：绿点=保留、红点=去除，
提交时按颜色直接生效，与「作用」下拉当前值无关。

根因②：「开始处理」从未消费画布上未提交（pending）的涂抹/区域，
它们既不进裁决层也不清除，就一直画在那里。

修复：
- gui.py `_build_selection_masks()`：fg_pts→keep、bg_pts→drop（颜色即语义，
  M13 起「点选」的颜色在绘制时就已确定）；regions（矩形框/描边/套索）没有
  颜色语义，仍按「作用」下拉当前值整体处理。
- canvas.py 新增 `take_selection()`：取走全部未提交内容并清空画布；
  gui.py `_process()` 开头调用它，把还没按 Enter 的涂抹自动并入裁决层。
- `_clear_override()` 同步清掉画布 pending，避免"清除手动修改"后又被并回来。

改动文件：src/ui/canvas.py、src/ui/gui.py。

验证：[14] 8/9 项 GUI 断言（绿点→保留、红点→去除、区域受作用下拉控制、
未提交涂抹自动并入且画布清空）。

## 四、本期关键经验（浓缩）

1. "后画的覆盖先画的"才是用户反悔心智；"防误删"只在**同一笔内部**成立，

2. 交互数据在**产生时**带语义（颜色），消费时直接用；提交时按"当前状态"反推必错

4. 新引擎用**默认 + 自动回退**接入最稳：默认接管、遇纯色/缺模型落回原路径，
   旧引擎行为不变，回归测试因此全绿。
5. 分辨率是分割模型硬上限；onnxruntime 内存池对单张大输入反复推理要显式关掉
   `enable_mem_pattern` 与 `enable_cpu_mem_arena`。

# 修复：运行 exe 后窗口/任务栏没有图标（Qt 不继承 exe 内嵌图标）

现象：exe 已用新 logo 重建，但运行后①窗口标题栏/任务栏仍是通用图标；②资源管理器里
exe 文件图标也还是通用图标。
根因（两个独立问题）：
  1. 窗口图标：全项目**没有任何 `setWindowIcon`**。PyInstaller 的 `EXE(icon=...)` 只负责
     给 exe **文件**挂图标资源，Qt 窗口/任务栏图标**不会**自动继承它——必须由代码显式设置。
  2. exe 文件图标：图标其实**已经正确内嵌**（解析 PE 资源表：RT_ICON(#3) 7 个条目、
     RT_GROUP_ICON(#14) 1 个），资源管理器显示旧图标是 **Windows 图标缓存**未刷新。
修复：
  - 新增 `src/ui/resources.py`：`resource_path()` 兼容开发态（项目根）与冻结态（`sys._MEIPASS`），
    `app_icon_path()` 返回 ico 路径；
  - `src/app.py`：`QApplication.setWindowIcon(QIcon(app_icon_path()))`（覆盖所有窗口与任务栏）；
  - `src/ui/gui.py`：`MainWindow.__init__` 里再显式 `self.setWindowIcon(...)` 加固；
  - `build.spec`：把 `assets/logo/lucentcut.ico` 加入 `datas`，冻结后位于
    `<_MEIPASS>/assets/logo/lucentcut.ico` 供运行时读取（与 exe 文件图标是两件事）。
验证：
  - offscreen 实测 `QIcon` 非空、含 7 个可用尺寸；
  - 自测 149 项全绿；
  - 重建 exe 后解析归档：RT_ICON 7 条 + 归档内含 `assets\logo\lucentcut.ico`；
  - 构建日志 `Copying icon to EXE`。
经验：
  1. **exe 文件图标 ≠ 窗口/任务栏图标**。前者靠 `EXE(icon=)`，后者必须 `QApplication.setWindowIcon`，
     且图标文件要随包 `datas` 打进冻结目录，否则打包后代码找不到文件。
  2. 用了 `sys._MEIPASS` 的资源路径务必写统一工具函数，避免散落的 `__file__` 相对路径在冻结后失效。
  3. exe 图标不刷新优先怀疑 Windows 图标缓存，不要急着重建。
